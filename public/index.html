AGENT PIPELINE

Five Agents, One Explainable Decision

Each agent has a defined contract, isolated responsibility, and produces structured output that flows into the next stage.

📥
A1
Ingest
Ingest Agent DOCUMENT GATEKEEPER
Validates document completeness before any processing begins. Classifies each file using Gemini Flash as PRESCRIPTION, HOSPITAL_BILL, LAB_REPORT, PHARMACY_BILL, or DISCHARGE_SUMMARY. Checks readability and flags duplicates. If any required document is missing or unreadable, sends a RESUBMISSION_REQUIRED request and holds the claim — never rejects.
COMPLETE INCOMPLETE UNREADABLE → HITL
↓ enriched claim passes to extraction
🔍
A2
Extract
Extraction Agent IDP ORCHESTRATOR
Calls the four-engine IDP stack per document. Selects highest-confidence field values. Cross-matches patient names across all documents — any mismatch halts the pipeline. Validates doctor registration number formats. Expands medical shorthand (HTN → Hypertension, T2DM → Type 2 Diabetes Mellitus). Ops can edit any extracted field; edits are audit-logged.
PATIENT_MATCH PATIENT_MISMATCH → halt LOW_CONFIDENCE → HITL
↓ structured fields pass to risk scoring
🛡️
A3
Risk
Risk & Integrity Agent FRAUD SCORER
Evaluates six risk signals: same-day claim count, monthly claim count, high-value threshold (₹25,000+), duplicate claim hash, document alteration flags from IDP, and provider overuse patterns. Each flag contributes a weighted score capped at 1.0. Never auto-rejects — routes to MANUAL_REVIEW for human judgment above the 0.80 threshold.
PASS (score < 0.80) MANUAL_REVIEW (score ≥ 0.80)
↓ verified claim runs through policy rules
📋
A4
Policy
Policy Engine Agent RULE EVALUATOR
Runs 12 sequential checks in deterministic order: member eligibility, policy active status, submission deadline, minimum amount, initial waiting period (30 days), condition-specific waiting periods (up to 730 days), exclusion matching, pre-authorization for high-value diagnostics, coverage category, per-claim limit, sub-limit cap, and annual OPD limit. All rules loaded from policy_terms.json — zero hardcoding.
ELIGIBLE PARTIAL (capped) REJECTED + reason code
↓ policy verdict enters final adjudication
⚖️
A5
Adjudicate
Adjudication Agent FINAL CALCULATOR
Applies financial calculations in the contractually correct sequence: network discount first, co-pay second, branded drug co-pay on pharmacy line items. Aggregates all agent results into a confidence score (starting at 1.0 with deductions for IDP failures). Generates a structured reason card with the full evidence chain. Claims above ₹25,000 or confidence below 0.60 require Ops confirmation before the decision is written.
APPROVED PARTIAL REJECTED MANUAL_REVIEW
HUMAN-IN-THE-LOOP

Automation Handles Routine.
You Handle Exceptions.

HITL checkpoints are embedded at every stage so Ops can review, correct, or escalate without re-running the entire pipeline.

TRIGGER: MISSING DOCUMENT
Document Resubmission Request
When a required document is missing or misclassified, Ops reviews the specific error and sends a resubmission request via the Member Portal — naming the exact document type needed.
→ Member uploads missing file → pipeline resumes
TRIGGER: UNREADABLE DOCUMENT
Re-upload Request
When IDP cannot extract fields reliably from a photo or scan, Ops inspects the preview and either accepts the extraction or sends a targeted re-upload request for that specific file.
→ Member re-uploads → pipeline restarts from Agent 2
TRIGGER: PATIENT MISMATCH
Cross-Document Identity Review
When patient names differ across documents (e.g. "Rajesh Kumar" on prescription vs "Arjun Mehta" on bill), Ops sees both names and the source files. They confirm or reject the mismatch.
→ Rejected by Ops = REJECTED(PATIENT_MISMATCH)
TRIGGER: LOW CONFIDENCE FIELD
Field Value Editing
For fields below the confidence threshold, Ops can directly edit the extracted value in the console. Every edit is stored in the audit trail with the editor's identity and timestamp.
→ Corrected value propagates to Policy Engine
TRIGGER: FRAUD SCORE ≥ 0.80
Risk Flag Review
All flagged signals and supporting evidence are surfaced for Ops to validate or reject. Ops records a reason code which is synced to the Claims System, Enrollment System, and Member Portal.
→ Ops decision logged with full evidence trail
TRIGGER: CLAIM AMOUNT ≥ ₹25,000
High-Value Confirmation
High-value claims are held for mandatory Ops confirmation before the decision is written. Ops reviews the full calculation breakdown — network discount, co-pay, and approved amount — before approving.
→ Final approval only after Ops sign-off
TRIGGER: COMPONENT FAILURE
Degraded Pipeline Review
When an agent component fails, the pipeline continues with reduced confidence. Ops reviews the incomplete trace and the skipped component's note, then confirms or escalates.
→ Failure logged; MANUAL_REVIEW recommended
TRIGGER: POLICY EDGE CASE
Policy Override
For claims that fall in ambiguous policy territory, Ops can override or confirm the Policy Engine's interpretation. The override is stored with the Ops user ID and reason, and the reason card is updated.
→ Override stored; reason card updated
DOCUMENT INTELLIGENCE

Four-Engine IDP Stack

No single OCR engine handles every Indian medical document. Plum OPS uses a tiered extraction strategy — highest-confidence field value wins.

PRIMARY
Gemini Flash
Vision LLM — handles handwriting, regional languages, rubber stamps, shorthand expansion, and partial documents in a single structured JSON prompt.
SECONDARY
PaddleOCR
Multilingual OCR for Hindi, Tamil, Telugu. Superior on low-contrast and skewed images. Runs on fields where Gemini confidence falls below threshold.
FALLBACK
Tesseract
Tertiary fallback for clean, printed documents and structured table extraction from diagnostic lab reports. Runs when PaddleOCR confidence is still insufficient.
ENTERPRISE
Azure Form Recognizer
Production-grade structured extraction with pre-built models for invoices, receipts, and prescriptions. Adapter interface allows hot-swap without pipeline changes.

USER GUIDE

How to Execute the Plum OPS Workflow

Step-by-step guide for Ops users to run claims smoothly through the platform from intake to settlement.

STEP 1
Review Incoming Claims
  • Open the Claims System tab in the left sidebar to see all incoming claims with their submission channel (email, portal, EDI).
  • Verify the claim ID has been mapped to the correct member in the Enrollment System tab.
  • Check the Member Portal tab to confirm the member's current policy status and YTD usage before running the pipeline.
TIP: Use the Overview dashboard for a summary of all pending claims and their current stage.
STEP 2
Run the Ingest Agent
  • Navigate to Agent 1 — Ingest Agent and click "Run Agent". The agent will classify all documents and check completeness.
  • Review the terminal log output for any missing document types or readability warnings.
  • If documents are missing: use the HITL action panel to send an email request to the member or provider asking them to resubmit the specific named document.
  • Wait for the member to re-upload, then re-run Agent 1 to confirm completeness before proceeding.
STATUS: COMPLETE → proceed to Agent 2. INCOMPLETE → send HITL resubmission request and hold.
STEP 3
Run the Extraction Agent
  • Navigate to Agent 2 — Extraction Agent and click "Run Agent". IDP engines will extract fields from each document.
  • Review per-field confidence scores in the split-pane extraction view. Fields below 0.65 are flagged in yellow — click to edit directly.
  • If a patient name mismatch is detected, review both source documents side by side and confirm or reject. A rejection halts the pipeline.
  • For any unreadable document, use the HITL panel to request a cleaner re-upload from the member.
EDIT: All field edits are audit-logged with your user ID and timestamp automatically.
STEP 4
Run Risk & Policy Agents
  • Run Agent 3 — Risk & Integrity. Review the fraud score and any flagged signals (same-day count, monthly count, duplicate hash).
  • If the fraud score exceeds 0.80, review the evidence cards carefully. Use the HITL panel to validate or reject the claim with a documented reason code.
  • Run Agent 4 — Policy Engine. Review the 12-point check results. Any REJECTED status will show the exact rule, the member's value, and the policy threshold.
  • For partial approvals, verify which line items were excluded and confirm the exclusion reason is documented correctly.
FRAUD RULE: Scores ≥ 0.80 OR claims ≥ ₹25,000 require Ops confirmation before proceeding.
STEP 5
Final Adjudication & Approval
  • Run Agent 5 — Adjudication Agent. Review the full settlement breakdown: network discount, co-pay deduction, and approved amount.
  • For claims above ₹25,000 or confidence below 0.60, the decision will be held in PENDING_OPS_REVIEW — you must click "Confirm & Approve" or "Reject" to release it.
  • Review the reason card to ensure all evidence fields, rule names, and member-facing explanations are complete and accurate.
  • Confirm the decision. The system will automatically sync the outcome to the Claims System, Enrollment System, and Member Portal.
DECISION CODES: APPROVED / PARTIAL / REJECTED / MANUAL_REVIEW — each has a structured reason card.
STEP 6
Audit Log & Post-Processing
  • Open the Audit Log tab to verify all agent stages, HITL actions, and sync events are recorded for the claim.
  • Confirm the member has received a portal notification with a plain-language explanation of the decision and the approved amount.
  • For MANUAL_REVIEW decisions, document your validation reason in the HITL action panel before closing the case.
  • Use the Settings tab to adjust thresholds (confidence, fraud cutoff, high-value limit) as needed for policy updates.
AUDIT RULE: Never close a claim without a complete reason card. Every rejection must name the exact rule and the member's first eligible date (for waiting periods).
